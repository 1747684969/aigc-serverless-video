# 架构与设计取舍

## 1. 需求与约束

| 约束 | 具体值 |
|---|---|
| 本地显存 | **4GB**（RTX 3050 Laptop） |
| 模型体积 | **约 26GB**（UNet int8 ~9GB + Qwen3VL-32B 文本编码器 ~17GB） |
| 任务特征 | **突发型**：出片集中在某段时间，其余时间完全空闲 |
| 输出要求 | 视频 + **原生立体声**，24fps，可放大到高分辨率成片 |

**核心矛盾**：本地装不下模型，但租常驻 GPU 又长期空转浪费。

---

## 2. 架构选择

```
本地（编排 + 校验 + 后处理）  ←→  Modal（按需 GPU 推理）
                                        ↕
                              Modal Volume（26GB 模型）
```

### 为什么是「云端推理 + 本地编排」

| 方案 | 结论 |
|---|---|
| 本地全量推理 | ❌ 4GB 显存 vs 26GB 权重，不可能 |
| 常驻云 GPU | ❌ `keep_warm=1` 一天约 $79，个人使用不划算 |
| **Serverless GPU（采用）** | ✅ 有请求才计费，无任务时零计算费用 |
| 换更小的量化模型 | ❌ nvfp4 需 Blackwell；换更小底模直接损质量 |

---

## 3. 关键设计决策

### 3.1 模型放 Volume，而不是打进镜像

| 方案 | 代价 |
|---|---|
| 打进镜像 | 镜像膨胀 9GB+17GB，每次部署极慢 |
| **放 Modal Volume（采用）** | 网络挂载读取（冷启动 3–6 min），存储 ≈$0.57/月 |

模型体积决定了不能进镜像。代价是冷启动要读 26GB —— 这是**当前架构的主要成本来源**，
因此优化重点放在「**减少冷启动次数**」而非「压缩单次计算」。

### 3.2 容器内 `Popen` 拉起无头 ComfyUI

不重写推理管线，而是**在云端容器里跑一个无头 ComfyUI**，通过它的 HTTP API 提交工作流。

**收益**：
- 直接复用 ComfyUI 官方节点生态与工作流语义；
- 本地与云端的图结构一致，调试成本低；
- 换模型/换采样器不需要改推理代码。

**代价**：容器启动多花 0.5–1 分钟，且需要处理 `/object_info` 的版本差异。

### 3.3 `scaledown_window`（热容器保活）

```python
scaledown_window=120   # 单位：秒
```

保活期间重复请求**直接复用已加载到显存的模型**，跳过 3–6 分钟的加载。

| 使用习惯 | 建议 |
|---|---|
| 连续出片（连拍） | 调大到 300–600s，收益最大（省 ~75%） |
| 出一片就走 | 调小（如 30–60s），否则多付闲置费 |

> 这是一个**按使用模式调节**的参数，没有全局最优值。

### 3.4 动态节点探测（防上游变更）

云端 ComfyUI 是运行时 `git clone` 最新代码，节点集合会变。因此提交前先查 `/object_info`：

```
CreateVideo + SaveVideo 可用？ → 用核心节点
否则 VHS_VideoCombine 可用？   → 用 VHS 插件
否则                           → 明确报错
```

### 3.5 客户端与服务端超时成对设计

| 层 | 超时 |
|---|---|
| 云端 Modal 函数 | 1200s |
| 本地节点 | **1500s**（必须更大） |
| 本地轮询 `/history` | 840s |

原则：**客户端超时必须大于服务端**，否则会出现"服务端算完了、客户端已放弃"——钱花了、结果丢了。

### 3.6 画布与帧数的模型原生约束

| 约束 | 处理 |
|---|---|
| 宽高必须 32 的倍数 | `_snap32()` 自动对齐 |
| 短边上限 768（原生 16:9 = 1280×736） | 超限自动收敛，过小自动提升 |
| 帧数按 17k+5 网格 | `length = base + (5 - base % 17) % 17` |

**为什么必须做**：偏离训练分布的分辨率/帧数会导致画面异常，且这些问题**表现为"模型质量差"**，
很难归因——所以要在入口处强制约束，并打印调整说明。

### 3.7 结果指纹复用

对影响生成结果的字段做 SHA256 指纹（prompt/seed/size/duration/turbo/模型名/首尾帧…），
落盘时写入 `.json` 元数据；下次请求指纹一致时**直接复用本地成片，不调用云端**。

> 注意：指纹**只覆盖影响结果的字段**，避免把无关变化（如日志字段）算进去导致缓存失效。

### 3.8 三级解码兜底

`decode_video_frames()`：**PyAV → OpenCV → ffmpeg**，全部失败才报错并附各层详情。

其中 PyAV 路径做了内存优化：预分配 float32 数组逐帧写入、容量不足翻倍、`/= 255.0` 用 in-place，
**峰值内存降低约 30–50%**。

## 4. 请求时序

```
本地                                     云端
 │                                        │
 ├─ 构建 payload（prompt/seed/尺寸/帧数）  │
 ├─ 画布对齐 + 帧网格吸附                 │
 ├─ 指纹比对 ──命中──► 复用本地成片（结束）│
 │                                        │
 ├─ POST /  (1500s timeout) ─────────────►│ 容器启动（冷启动读 26GB）
 │                                        │ 拉起无头 ComfyUI
 │                                        │ 组装工作流 → /prompt
 │                                        │ 轮询 /history
 │                                        │ 视频+音频双解码 → 封装 MP4
 │◄──────── video/mp4 字节流 ─────────────┤
 ├─ 魔数校验（_looks_like_video）
 ├─ 落盘 + 写指纹元数据
 ├─ PyAV 探测参数（分辨率/fps/帧数/音频流）
 ├─ 解码为 IMAGE 张量（三级兜底）
 └─ 封装为 ComfyUI VIDEO 对象（含音频）
```

---

## 5. 数据流与体积

| 项 | 量级 |
|---|---|
| 上行（payload） | 几 KB（首尾帧为 PNG base64，百 KB 级） |
| 下行（MP4） | 几 MB |
| 云端模型读取 | **26GB / 次冷启动** ← 真正的瓶颈 |
| 本地解码张量 | 124 帧 × H × W × 3 × float32（4GB 显存下需注意峰值） |
